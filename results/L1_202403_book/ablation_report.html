External Venue Documentation & Parameterized Assumptions

  • Hyperliquid: intra-batch priority order: Official docs (hyperliquid-l1/order-book) state that within each consensus batch, non-GTC/IOC actions (i.e. post-only / ALO) are processed first, followed by cancels, followed by GTC/IOC orders. Thus new MM post-only quotes land before cancels and takers without a dead gap. Model this with `--b-batch-order hl`. Source: https://hyperliquid.gitbook.io/hyperliquid-docs/hyperliquid-l1/order-book
  • Hyperliquid: block interval & buckets: Official docs (for-developers/api/priority-fees) state that IOC orders are sorted in 70 ms unix-time buckets, typically corresponding to one block (with 1-2 consensus batches per block, meaning effective batch windows may be shorter than 70 ms). End-to-end co-located latency is cited around ~0.2 s median in third-party mirrors. Source: https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/priority-fees ; https://hyperliquid.gitbook.io/hyperliquid-docs/hypercore/overview
  • dYdX Chain (v4): block time: The official onboarding FAQ states an average block time of about 1 second, and that short-term order cancels are best effort until the block is final. Use `--b-window-ms 1000` to evaluate a 1-second batching cadence. Source: https://docs.dydx.xyz/concepts/onboarding-faqs
  • Not documented (stay parameterized assumptions): No venue documentation specifies MM reaction time, market-data feed latency, client-to-sequencer network transit, or latency-arbitrageur reaction time. Defaults (feed 5 ms, MM reaction 10 ms, sniper reaction 2 ms, network 30 ms) are parameterized assumptions; sweep `--mm-react` rather than trusting a single point. Source: n/a

Dywe Protocol Design Parameters & Threat Model

  • Dywe micro-batch window & threshold decryption RTT: The 50 ms micro-batch window and 35 ms / 70 ms threshold decryption RTTs are Dywe protocol design parameters, not live multi-region Devnet measurements.
  • Unified post-decrypt threat model: All order messages (New ALO, Cancel, Taker) are threshold-encrypted client-side (BLS12-381) until batch_close. Threshold decryption completes in matching-engine memory at clear_ns = batch_close + decrypt_ms before the first fill executes, enabling deterministic New (ALO) -> Cancel -> Taker ordering (--d-batch-order hl) without leaking ALO/IOC flags pre-commit. The leak_ppm grid models potential residual side-channel/timing leakage on batches with MM cancels (0% under full cryptographic payload/metadata padding; 10%-50% stress sensitivity).
  • Stylized model disclaimer: Regimes B (70 ms / 200 ms / 1000 ms) are stylized batching models, not byte-for-byte reproductions of Hyperliquid or dYdX matching engines.

Methodological Scope & Statistical Boundaries

  • Regime D timeline: all order fields (New ALO, Cancel, Taker) are threshold-encrypted pre-commit, commit at batch_close, complete threshold decryption at clear_ns = batch_close + decrypt_ms, and clear in matching-engine memory using hl ordering. Windows: B 70ms (hl), C 100ms, D 50ms (hl).
  • Simulated latency-arb probe: StaleSnipe hits are generated by a deterministic parameterized probe (2 bps trigger, 2 ms reaction, $25000 clip; configurable via --sniper-clip).
  • Selection bias under drop: when pending=drop, takers arriving during an MM cancel-replace gap are excluded from both MM markout and All-In Net; compare Dropped Takers (USD%) before comparing costs across regimes.
  • Single-denominator additivity: --wait-cohort all (default) computes waiting drift over all executed takers (tk_n), matching the denominator of Spread Paid, Taker Stale, and MEV Taker.
  • 95% bootstrap CI: joint 3-hour block resampling across BTCUSDT and ETHUSDT (24 blocks). It reflects drift variance under fixed scenario assumptions and does not cover parameter uncertainty (capture, impact, leak, reaction times, windows).
  • Other limits: exogenous taker flow (invariant to spread width), one representative MM clearing the entire exchange flow, absolute s*net levels not directly comparable to real Binance tick spreads, and limited sample windows.
