External Venue Documentation & Parameterized Assumptions

  • Hyperliquid: intra-batch priority order: Official docs (hyperliquid-l1/order-book, accessed Nov 2026) state that within each consensus batch, non-GTC/IOC actions (i.e. post-only / ALO) are processed first, followed by cancels, followed by GTC/IOC orders. Model this with `--b-batch-order hl`. Source: https://hyperliquid.gitbook.io/hyperliquid-docs/hyperliquid-l1/order-book
  • Hyperliquid: block interval & buckets: Official docs (for-developers/api/priority-fees, accessed Nov 2026) state that IOC orders are sorted in 70 ms unix-time buckets, typically corresponding to one block (with 1-2 consensus batches per block). End-to-end co-located latency is cited around ~0.2 s median in third-party mirrors. Source: https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/priority-fees ; https://hyperliquid.gitbook.io/hyperliquid-docs/hypercore/overview
  • dYdX Chain (v4): block time: Official onboarding FAQ (accessed Nov 2026) states an average block time of ~1 second and best-effort short-term cancels until block finality. Use `--b-window-ms 1000` to evaluate a 1-second batching cadence. Source: https://docs.dydx.xyz/concepts/onboarding-faqs
  • Not documented (parameterized assumptions): No venue documentation specifies MM reaction time, requote threshold, feed latency, client-to-sequencer transit, or sniper reaction time. Sweep `--mm-react` (e.g. 1,2,5,10,25,40) and `--requote-thr-sub` (e.g. 15,50,150) rather than trusting a single point. Source: n/a

Dywe Protocol Design Parameters & Threat Model

  • Dywe micro-batch window & threshold decryption RTT: The 50 ms micro-batch window and 35 ms / 70 ms threshold decryption RTTs are Dywe protocol design parameters, not live multi-region Devnet measurements. No BLS12-381 cryptographic operations are executed inside this microstructure simulator.
  • Unified post-decrypt threat model & exposure mode: All order messages (New ALO, Cancel, Taker) are threshold-encrypted client-side (BLS12-381) with uniform frame padding until batch_close, decrypting in matching-engine memory at clear_ns = batch_close + decrypt_ms before New (ALO) -> Cancel -> Taker sorting (`--d-batch-order hl`). Under `--d-exposure-mode all` (default), `eff_leak = min(leak_ppm, capture_ppm)` applies uniformly across all large bursts; under `cancel-batch` (legacy v0.3.4), it applies only to batches containing an MM cancel.
  • Stylized model disclaimer: Regimes B (70 ms / 200 ms / 1000 ms) are stylized batching models, not byte-for-byte reproductions of Hyperliquid or dYdX matching engines.

Methodological Scope & Statistical Boundaries

  • Regime D timeline & exposure: orders commit at batch_close, decrypt at clear_ns = batch_close + decrypt_ms, and clear using hl ordering. Windows: B 70ms (hl), C 100ms, D 50ms (hl). Exposure mode: all.
  • MM requote & sniper probe parameters: representative MM requotes when mid moves ≥1.500 bp (--requote-thr-sub); synthetic probe triggers at ≥2.000 bp (--sniper-thr-sub) with 2 ms reaction and $25000 clip (--sniper-clip).
  • 1-ms burst aggregation: merge_taker aggregates same-millisecond, same-direction executions; inspect Raw Taker Diagnostics above for the unmerged lower bound.
  • 95% bootstrap CI: joint 3-hour block resampling (24 blocks). Quantifies drift sampling variance under fixed scenario assumptions and does not account for volatility autocorrelation or parameter uncertainty.
